## 🎯 Задача

Продолжить существующий LogHub: обработать записи смешанного потока настраиваемой цепочкой фильтров, выполнять операции над тремя видами записей посетителями и уведомлять независимых подписчиков. Сохранить импортёры, автоопределение PIPE/JSON и два приёмника варианта 20. Дополнительно связать ограниченный буфер конвейера и импорт через Посредника.

Основание: [`Практикум/ЛР4_Конвейер_обработки.md`](../Практикум/ЛР4_Конвейер_обработки.md) и «Практикум.pdf», с. 4, 20–22. В учебном PDF работа имеет номер 7 в сквозной нумерации занятий, в репозитории — ЛР4; для сдачи используются `docs/ЛР4.md` и `feature/лр-4`.

## 💡 Ключевые решения

### 1️⃣ Формат источника и вид записи — разные понятия

Сохраняются ровно два входных формата: PIPE и JSON Lines. `LogParser.Parse` определяет формат каждой строки по её содержимому, а не по имени файла или первой записи. PIPE сохраняет прежнюю форму `дата|уровень|сообщение`; разделитель внутри сообщения не теряется, потому что используется `Split('|', 3)`.

`LogRecord` стал абстрактным общим типом. Его свойства доступны только для начальной инициализации: подписчик не может изменить запись, которую затем получит другой подписчик. `SimpleLogEntry`, `ExceptionLogEntry` и `MetricLogEntry` самостоятельно переопределяют `Accept`.

PIPE и JSON без поля `kind` создают `SimpleLogEntry`. JSON с `kind=exception` дополнительно требует непустое строковое поле `stackTrace`; JSON с `kind=metric` — конечное числовое поле `value`. Неизвестный `kind` считается ошибкой входной строки. Это расширение уже существующего JSON-формата, не третий формат источника.

```text
2026-10-07T11:30:00|Info|Приложение запущено
{"date":"2026-10-07T11:30:01Z","level":"Critical","message":"Сбой","kind":"exception","stackTrace":"at Service.Run()"}
{"date":"2026-10-07T11:30:02Z","level":"Info","message":"CPU","kind":"metric","value":42.5}
```

Проверка текстового поля `kind` при десериализации не подменяет Посетителя: после создания объектов операции над ними выполняются через `Accept/Visit`, без `is`, `switch` по типу или pattern matching.

### 2️⃣ Порядок цепочки имеет наблюдаемый смысл

Профиль задаёт `filters=severity,age,duplicates`. `CompositionRoot` обнаруживает конкретные наследники `LogFilter`, а `FilterChain` связывает только выбранные имена в указанном порядке. Новому фильтру достаточно собственного класса с `Name` и реализацией `Allows`; центральный список классов править не нужно.

Пустое значение `filters=` означает пустую цепочку, пропускающую все уже разобранные записи. Синтаксически неверные строки по-прежнему отвергаются импортёром — пустая цепочка не превращает некорректный текст в запись. Неизвестное имя фильтра и повтор одного имени вызывают понятную ошибку, а не молча игнорируются.

Возраст сравнивается с `TimeProvider`. Воспроизводимый профиль содержит `referenceTimeUtc=2026-10-07T12:00:00Z`; обычный профиль без этого поля использует системные часы. Время без указанного часового пояса считается UTC. Граница возраста включительна; будущая запись не считается старой.

Ключ дубликата включает вид, уровень, сообщение и дополнительные данные вида; дата исключена. Таким образом, повтор сообщения позднее всё ещё является дубликатом, но метрики с разными значениями и исключения с разными стектрейсами различаются. Память дубликатов очищается перед каждым запуском.

Чтобы показать влияние порядка, файл `data/order-demo.txt` содержит сначала старую PIPE-запись, затем свежую JSON-запись с теми же уровнем и сообщением:

| Порядок | Старое сообщение | Свежее сообщение | Принято |
|---|---|---|---:|
| `severity,age,duplicates` | Отсекается по возрасту до проверки дубликата | Ключ ещё не встречался | 1 |
| `duplicates,age,severity` | Сначала запоминает ключ, затем отсекается по возрасту | Отсекается как повтор | 0 |

Дедупликация запоминает запись при достижении своего звена, даже если её затем отвергнет следующее звено. Это выбранная и явно проверяемая семантика.

### 3️⃣ Двойная диспетчеризация

Клиент располагает ссылкой `LogRecord`, но вызывает виртуальный `Accept`. Выполняется реализация конкретного класса, где статический тип `this` уже известен компилятору:

```csharp
public override void Accept(ILogEntryVisitor visitor)
{
    ArgumentNullException.ThrowIfNull(visitor);
    visitor.Visit(this);
}
```

Поэтому выбирается нужная перегрузка `Visit(SimpleLogEntry)`, `Visit(ExceptionLogEntry)` или `Visit(MetricLogEntry)`. Вынести тело в базовый `LogRecord` нельзя: там `this` имеет тип `LogRecord`, а такой перегрузки интерфейс намеренно не содержит.

`LogFormatter` из предыдущих работ теперь сам реализует посетителя, сохраняя метод `Format(LogRecord)`. Помимо обычного текста, сохраняются конфигурируемые выходные JSON и CSV. JSON формируется сериализатором; строковые символы экранируются, а значение метрики остаётся числом. `StatisticsVisitor` считает принятые записи каждого вида. Третий посетитель, `DuplicateKeyVisitor`, формирует ключ для фильтра дубликатов. В тестовой сборке есть ещё один посетитель `TypeNameVisitor`, добавленный без правки классов записей.

### 4️⃣ Push и pull действительно разделены

В push подписчик получает `ProcessedLog` непосредственно в `OnProcessed(item)`. В pull вызывается `OnChanged(source)`: передаётся только ссылка на источник, а текущую запись подписчик сам читает через `source.Current`. Полезная нагрузка не передаётся в pull-уведомлении как аргумент записи.

`LogObserver` объединяет общую операцию подписчика, но не смешивает протоколы: его push-метод использует аргумент, а pull-метод читает источник. Профили `pipeline-push.config` и `pipeline-pull.config` используют одинаковые данные и правила; отличия — способ уведомления и выходной файл.

Для небольшой неизменяемой записи push проще: подписчику сразу доступны нужные данные. Pull удобен, когда реакциям нужны разные части состояния или само состояние велико. В этой реализации `Current` — текущая запись, а не история; уведомления синхронные и последовательные. Повторная публикация из обработчика запрещена и регистрируется как ошибка этого подписчика, чтобы следующий pull-подписчик не прочитал случайно другую запись. Для асинхронного варианта потребовался бы отдельный контракт снимков или версий.

### 5️⃣ Подписчики, отписка и ошибки

В рабочем профиле четыре независимых подписчика: счётчик, алерт Critical, `SinkObserver<ConsoleLogSink>` и `SinkObserver<FileLogSink>`. Запись в приёмники выполняется только наблюдателями; дополнительного прямого вывода той же записи из процессора нет.

Обе операции подписки возвращают `IDisposable`. Освобождение токена удаляет конкретную подписку и освобождает удерживаемые ссылки. Повторный `Dispose` безопасен. `PipelineSubscriptions` освобождает все токены при завершении работы контейнера.

Каждый подписчик вызывается в своём `try/catch`. Исключения сохраняются в `PipelineEvents.Failures`, а остальные подписчики продолжают работу. Программа печатает ошибки и после завершения возвращает код 2, если они были. Поэтому исключение при вызове уже созданного файлового подписчика не препятствует отправке записи консольному подписчику, но и не объявляется успешной записью на диск. Ошибка открытия файла при создании `FileLogSink` в эту защиту не входит: она возникает ещё при построении приложения.

Поле `ProcessingResult.Written` сохранено ради совместимости с тестами ЛР6; теперь оно явно означает число принятых/обработанных записей, а не число физических записей в приёмники. Отдельно учитывается `NotificationErrors`. В консольном резюме используется подпись `Processed`.

Алерты и итоговое резюме — дополнительные строки консольной диагностики. Файловый приёмник получает только отформатированные записи; число строк всего консольного вывода поэтому не равно числу записей.

### 6️⃣ Посредник и реальная приостановка чтения

`ProcessingPipeline` содержит очередь ёмкостью `bufferCapacity`. При заполнении он сообщает об изменении давления через событие `PressureChanged`. Посредник получает это событие и вызывает `ImportSession.Pause()`. Пока сессия приостановлена, `TryRead` не вызывает `MoveNext` исходного перечислителя.

В `LogFlowMediator.Run` заполненный буфер обрабатывается, затем пустой конвейер сообщает о снятии давления, и посредник возобновляет импорт. Остаток неполной последней порции также обрабатывается. После завершения или исключения перечислитель освобождается, а неиспользованный буфер очищается.

Это однопоточная кооперативная модель, достаточная для демонстрации задания: ограничение очереди и запрет дальнейшего чтения реальны, но параллельный высоконагруженный сервис здесь не моделируется. В тестах нет ожиданий по времени и `Thread.Sleep`. При ошибке самого источника запуск завершается ошибкой; накопленные, но ещё не обработанные записи не объявляются успешно обработанными.

### 7️⃣ Совместимость с предыдущими работами

Сохранены три импортёра, невиртуальный шаблон импорта с хуком, независимые графовые итераторы, `IConfigService` и приёмники. Операции `LogProcessor.Run()` и `ChangeImporter()` остаются; непосредственное управление импортом и конвейером перенесено посреднику.

Конструирование процессора в прежних тестах обновлено под новые зависимости. Создание прежнего конкретного `LogRecord` заменено на `SimpleLogEntry`, но ожидаемые значения сохранены. Единственное содержательное изменение прежней проверки ошибок: исключение приёмника больше не должно прерывать весь запуск, поскольку ЛР7 требует изоляции ошибок подписчиков. Вместо ожидания выброса проверяются зарегистрированная ошибка и освобождение перечислителя.

У старых профилей явно задано `filters=severity`, чтобы новые возрастной фильтр и дедупликация не меняли демонстрацию ЛР3. Для ЛР4 подготовлены `pipeline-push.config` и `pipeline-pull.config`. Изменять учебные примеры в `DesignPatterns/` или конфигурацию CI для выполнения задания не требуется.

## ❓ Контрольные вопросы: привязка к решению

*   **Почему недостаточно обычной перегрузки?** Вызов посетителя с переменной типа `LogRecord` сам по себе не выбирает перегрузку по фактическому виду объекта. Сначала выбирается виртуальный `Accept`, затем внутри конкретного класса выбирается перегрузка `Visit(this)`.
*   **Почему не общий `Accept` в базе?** В базовом классе статический тип `this` — `LogRecord`. Перегрузок для конкретных классов этого недостаточно; нужная информация о конкретном типе должна присутствовать в собственном теле `Accept`.
*   **Недостаток Посетителя?** Новый вид записи потребует новой перегрузки в `ILogEntryVisitor` и изменений всех посетителей. Зато новая операция над существующими видами добавляется отдельным посетителем.
*   **Что происходит при исключении наблюдателя?** Наивный последовательный вызов мог бы прервать рассылку. Здесь каждый вызов изолирован, ошибка сохраняется, а следующий подписчик получает запись.
*   **Откуда утечка памяти?** Долгоживущий источник удерживает подписчика через список подписок и делегат. Токен отписки удаляет запись и обнуляет ссылки; контейнер освобождает комплект подписок.
*   **Чем цепь отличается от списка в цикле?** Каждое звено само решает, передавать ли запись дальше; после отказа следующие звенья не вызываются. Цикл в `FilterChain` используется только при сборке связей, а не для независимого запуска всех фильтров.
*   **Что происходит на конце цепи?** Для этой задачи достижение конца означает, что все выбранные проверки пройдены. Пустая цепь тоже возвращает разрешение; это явная семантика фильтрации.
*   **Чем Посредник отличается от Наблюдателя?** `PipelineEvents` рассылает уведомления независимым реакциям. `LogFlowMediator` знает участников и принимает управляющее решение, когда остановить и продолжить импорт; это не просто ещё один писатель событий.

## ⚠️ Что не получилось

Успешный запуск сборки зафиксирован.

Наиболее нетривиальным решением стала **семантика порядка фильтров**: дедупликация фиксирует ключ сразу, поэтому перестановка фильтров действительно меняет результат. Другим существенным решением стало разделение уведомления о факте изменения в pull и передачи готовой записи в push при гарантии, что ошибка одного наблюдателя не прервёт остальные. Для посредника отдельно проверяется, что пауза прекращает чтение из импортёра, а не просто изменяет счётчик.

Принятые ограничения: обработка последовательная и не рассчитана на конкурентные публикации; множество дубликатов хранится до конца запуска и для бесконечного потока потребовало бы ограниченного окна; автоматических повторных попыток и гарантированной доставки при отказе приёмника нет. Эти возможности не требуются текущим заданием и не заявляются как реализованные. Рендеринг PlantUML и GitHub CI для PR ЛР4 нуждаются в окончательной проверке.
