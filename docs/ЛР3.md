## 🎯 Задача

Продолжить LogHub из ЛР4–ЛР5: вынести получение записей в заменяемую стратегию и общий алгоритм чтения, сохранив смешанный формат варианта 20 и два приёмника. Для графа зависимостей реализовать независимые обходы **DFS** (в глубину) и **BFS** (в ширину) вручную и через `yield return`, включая вложенные перечисления и поиск пути цикла.

## 🧩 Применённые паттерны

| Паттерн | Где применён | Почему именно он |
|---|---|---|
| **Стратегия (Strategy)** | `ILogImporter` внедряется в `LogProcessor`; метод `ChangeImporter` меняет объект между запусками. | Источники дают одинаковое представление записи, но различаются способом чтения и допустимым форматом. Процессору не нужны проверки конкретного типа. Наследование процессоров привязало бы выбор всего источника к типу процессора. |
| **Шаблонный метод (Template Method)** | Невиртуальный `LogImporterBase.Import()`. | Открытие ресурса, порядок шагов, нумерация строк и гарантированное освобождение едины. Наследники реализуют `Read` и `Parse`; только смешанный импортёр дополнительно меняет `Validate`. |
| **Итератор (Iterator)** | `DependencyGraph`, `ManualTraversal`, два ручных перечислителя и два метода с `yield return`. | Граф хранит топологию, а не позицию обхода. Каждое перечисление получает собственные очередь/стек, посещённые вершины и текущую вершину. Это необходимо для вложенных циклов по тому же объекту. |

## 💡 Ключевые решения

### 1️⃣ Три импортёра и вариант 20

* `MixedLogImporter` читает смешанный поток.
* `JsonLogImporter` принимает только JSON Lines.
* `InMemoryLogImporter` читает текст из памяти.

В композиционном корне для первых двух выбран `FileTextSource`, для третьего — `InMemoryTextSource`. Интерфейс `ITextSource` позволяет проверять и файловые сценарии парсинга на `StringReader`, не обращаясь к диску.

Сохранены форматы предыдущей работы:

```text
2026-10-07T10:00:00|Info|Система запущена
{"date":"2026-10-07T10:01:00","level":"Error","message":"Ошибка подключения"}
```

`LogParser.Parse` определяет формат **каждой строки** после удаления внешних пробелов. Начало `{` направляет запись в JSON-разбор, остальные строки — в разбор PIPE. Это проверка формата записи, а не выбор стратегии источника. Выбор стратегии находится только в композиционном корне.

Профиль `profiles/variant20.config` содержит `importer=mixed` и `sink=console,file`. Поэтому обе записи одного потока направляются одновременно в консоль и файл. Настройки `importer` (вход) и `format` (выход) намеренно независимы.

### 2️⃣ Хук валидации и освобождение ресурсов

Общий порядок: `Open → Read → Parse → Validate → ... → Close → Release`. Шаги `Read` и `Parse` — абстрактные `protected`; `Validate` — виртуальный хук, который по умолчанию возвращает `true`. Сам `Import` не объявлен `virtual`.

Только `MixedLogImporter` переопределяет `Validate`: сообщение не должно быть пустым, а уровень должен быть одним из базовых. Вся работа с открытым `TextReader` находится внутри `try/finally`. Вложенный `finally` вызывает `Release` даже при исключении из `Close`. 

`Import()` возвращает **ленивую последовательность**: источник открывается при первом `MoveNext`, а не при получении `IEnumerable`. При ручном использовании перечислителя вызывающий код должен освобождать его через `using`; `foreach` делает это сам.

### 3️⃣ Интеграция с ЛР4–ЛР5

`LogProcessingModule` заменён на `LogProcessor`: получение и разбор строк теперь принадлежат импортёру. Старый `LogFileReader` удалён. Конфигурация и DI не обходятся: сервисы собираются в `CompositionRoot`, зависимости передаются через конструкторы.

Приёмники регистрируются по существующему атрибуту `SinkName`, без `switch` по именам. Обработчик получает `IEnumerable<ILogSink>`. Счётчик `Written` увеличивается **один раз на запись**, а не на каждый приёмник.

Пути входа и выхода разрешаются относительно **файла профиля**, а не текущего каталога терминала.

### 4️⃣ DFS, BFS и поиск цикла

Топология `DependencyGraph` неизменяема после конструктора. Корневая вершина входит в обход; несвязанные с ней компоненты в обход не входят.

* **DFS** использует стек (соседи помещаются в обратном порядке).
* **BFS** использует очередь (вершина отмечается при добавлении).

Для дерева `A → {B, C}`, `B → {D, E}`, `C → {F}` ожидается:
```text
DFS: A B D E C F
BFS: A B C D E F
```

`FindCycle()` — отдельная проверка активного пути DFS. Простое повторное достижение посещённой вершины недостаточно (общая зависимость — не цикл). Поиск проверяет все компоненты и использует явный стек кадров, а не рекурсию.

## ⚙️ Разбор yield return

В ручной версии `Current`, очередь/стек, `visited` и состояние завершения хранятся в отдельном объекте `IEnumerator<Node>`. `ManualTraversal.GetEnumerator()` каждый раз создаёт новый перечислитель.

Компилятор преобразует методы `DepthFirstCore` и `BreadthFirstCore` в объекты **машины состояний**. Позиция между `yield return` хранится в поле состояния, выданная вершина — в поле текущего значения. `MoveNext()` возобновляет выполнение до следующего `yield return`. Это не отдельный поток.

Типичные имена полей Roslyn — `<>1__state`, `<>2__current`, `<>4__this`. Контракты ручной и сгенерированной версии не тождественны во всех деталях: ручной `Reset()` поддержан, а у созданного компилятором итератора обычно бросает `NotSupportedException`.

Локальная сборка с `-warnaserror` прошла успешно, все активные тесты прошли, один унаследованный тест Singleton пропущен намеренно.

**Ограничения реализации:**
* Граф неизменяемый.
* `FindCycle()` возвращает первый найденный цикл, а не все циклы.
* Обработка синхронная.
* Смена импортёра предполагается между запусками, а не одновременно с обработкой.
