## Задание

### 1. Три реализации ConfigService

Реализуйте сервис конфигурации тремя способами:

| Вариант | Как | Файл |
|---|---|---|
| Классический синглтон | приватный конструктор, статический `Instance()` | `ClassicConfigService.cs` |
| Синглтон через `Lazy<T>` | `Lazy<T>` вместо ручной блокировки | `LazyConfigService.cs` |
| Обычный класс | публичный конструктор, время жизни задаёт контейнер | `ConfigService.cs` |

Все три реализуют один интерфейс `IConfigService` с методами
`GetValue(string key)` и `SetValue(string key, string value)`.

### 2. Показать проблему на тестах

Это главный пункт работы. Требуется **воспроизвести**, а не описать словами.

Напишите тесты ко всем трём реализациям так, чтобы:

* для классического синглтона существовал тест, который **проходит в одиночку
  и падает в наборе** (или наоборот) — потому что состояние переносится
  между тестами;
* для варианта через контейнер такого теста не существовало в принципе.

Проблемный тест пометьте `[Ignore("...")]` с объяснением в скобках,
иначе CI будет красным. Образец оформления — в учебном репозитории:
`Implementation.Tests/Singleton/ConfigServiceTest.cs`.

Запуск теста в одиночку:

```bash
dotnet test --filter "FullyQualifiedName~ИмяВашегоТеста"
```

### 3. Композиционный корень

Соберите LogHub из ЛР 1 на `Microsoft.Extensions.DependencyInjection`.

Требования:

* все зависимости приходят **через конструктор**;
* `new` для сервисов встречается только в композиционном корне;
* обращение к `IServiceProvider` — ровно одно, в точке входа.

Если где-то в коде появился `provider.GetService<T>()` — это Service Locator,
антипаттерн. Разбор, почему так делать не надо, —
в [главе про IoC](../Textbook/IoC_и_DI.md), раздел «Service Locator».

### 4. Подмена реализации конфигурацией

Сделайте два профиля — `console` и `file`. Переключение профиля должно
менять поведение системы **без перекомпиляции**: правится файл конфигурации,
приложение запускается заново.

## Типичная ошибка

**Зарегистрировать сервис в контейнере и продолжить обращаться к нему
через `Instance()`.**

Контейнер тогда не делает ничего: глобальная точка доступа никуда не делась,
тесты остались зависимыми от порядка выполнения. Формально DI есть,
фактически нет.

Проверьте себя: попробуйте написать тест, который подставляет свою реализацию
`IConfigService`. Если для этого приходится что-то сбрасывать статически —
внедрения зависимостей в вашем коде нет.
