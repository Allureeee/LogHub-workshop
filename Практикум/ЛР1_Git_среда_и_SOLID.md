## Часть A. Репозиторий и среда

### 1. Форк, клон, сборка

Выполните разовую настройку из раздела «Куда и как сдавать» общей части
практикума: форк, клон, `upstream`, ветка `develop`, защита `main`,
доступ преподавателю.

Затем проверьте, что всё собирается:

```bash
cd <репозиторий>/DesignPatterns
dotnet build
dotnet run --project Implementation -- --list
dotnet run --project Implementation -- abstract-factory
```

Если `dotnet build` не проходит — разберитесь с этим до всего остального.

### 2. Проверка процесса

Убедитесь, что настроено:

* `origin` — ваш форк, `upstream` — репозиторий преподавателя (`git remote -v`);
* ветки `main` (защищена) и `develop` (по умолчанию);
* преподаватель видит репозиторий.

### 3. Каркас LogHub

Создайте solution с двумя проектами: `LogHub` и `LogHub.Tests`.
Один проходящий тест обязателен — это проверка того, что тестовый проект
подключён правильно.

### 4. Непрерывная интеграция

Настройте GitHub Actions: сборка и тесты на каждый push.
За основу возьмите `.github/workflows/build.yml`
из учебного репозитория.

Убедитесь, что бейдж сборки зелёный. Дальше это условие приёмки каждой работы.

### 5. Чтение чужого кода

Выберите **любую** папку паттерна в `Implementation/`. Прочитайте её и:

* нарисуйте диаграмму классов на PlantUML;
* напишите в `docs/ЛР1.md` полстраницы: какая задача решается и как.

Это тренировка навыка, который дальше понадобится постоянно.

### 6. Релиз

Сделайте релиз `v0.1.0` с тегом:

```bash
git checkout main
git merge develop
git tag -a v0.1.0 -m "Каркас LogHub"
git push origin main --tags
```

## Часть B. Рефакторинг god-класса

### Вход

Класс `LogProcessingModule` лежит в учебном репозитории:
[Репозиторий: `_AntiPatterns/GodObject/LogProcessingModule.cs`](../DesignPatterns/Implementation/_AntiPatterns/GodObject/LogProcessingModule.cs)

Посмотрите исходное поведение:

```bash
dotnet run --project Implementation -- god-object
```

Класс одновременно читает конфигурацию, открывает соединение с БД,
разбирает строку лога, фильтрует, форматирует, решает по `switch`,
куда отправить, и пишет. Нарушены все пять принципов SOLID.

### Задание

**1. Найдите нарушения.** Составьте таблицу: какой принцип, в какой строке, почему.
Комментарии в файле подсказывают, где искать, но список неполный —
часть нарушений не помечена никак.

**2. Разделите класс на слои.** Чтение → разбор → фильтрация → форматирование → запись.
Ни один класс не должен иметь больше одной причины для изменения.

Проверочный вопрос к каждому получившемуся классу:
*кто придёт с требованием его изменить?* Если можете назвать двух разных
людей с разными интересами — обязанность одна не получилась.

**3. Уберите `switch` по типу приёмника** так, чтобы добавление нового приёмника
не требовало правки существующих файлов.

**4. Выделите интерфейсы там, где это оправдано.** И не выделяйте там,
где не оправдано: интерфейс с единственной реализацией, которую никто
не подменяет, — накладной расход. Лишние интерфейсы снимают балл
так же, как их отсутствие.

**5. Покройте тестами** разбор строки лога и маршрутизацию. Минимум 6 тестов.

**6. Дополните отчёт:** диаграмма классов до и после, абзац о том,
что стало проще менять.

### Как это проверяется

**Критерий OCP — механический.** На защите вас попросят добавить ещё один
приёмник (например, отправку в Telegram) и выполнить:

```bash
git diff --name-only
```

В выводе должны быть **только новые файлы**. Любой существующий файл
в списке означает, что OCP не соблюдён.

**Критерий DIP — через тесты.** Тесты не должны обращаться к диску,
сети и базе. `File.WriteAllText`, `Path.GetTempFileName` или строка
подключения в тесте означают, что DIP не соблюдён, даже если интерфейсы
формально выделены.

**Поведение не должно измениться.** Рефакторинг — это изменение структуры
без изменения поведения. Ваше решение и исходный `god-object` на одном
входном файле должны дать одинаковый вывод, включая счётчики записанного
и пропущенного. Не «улучшайте» заодно логику — это отдельная задача.

## Типичная ошибка

**Разнести код по файлам и решить, что SRP соблюдён.**

SRP — про причины изменения, а не про количество файлов. Пять файлов,
каждый из которых всё равно правится при смене формата логов, — это тот же
god-класс, только рассыпанный.

Об этом прямо сказано на слайде «Не усложняйте!» из материалов лекции №1:
больше файлов с классами не означает больше сложности, и наоборот —
меньше файлов не означает проще.
