# Лабораторная работа 4. Конвейер обработки

**Занятие 5** · 6 часов · вес в итоговой оценке 20%

## Цель

Собрать обработку записи лога из трёх поведенческих паттернов
и увидеть, где заканчивается зона ответственности каждого.

## Задание

### 1. Цепочка обязанностей — фильтры

Соберите конвейер фильтров:

```
по уровню важности → по возрасту записи → отсечение дубликатов → дальше
```

Требования:

* порядок звеньев задаётся **конфигурацией**, а не порядком вызовов в коде;
* цепочка корректно работает при пустом составе (пропускает всё);
* добавление нового фильтра не требует правки существующих.

### 2. Посетитель — операции над записями

Заведите три типа записей: `SimpleLogEntry`, `ExceptionLogEntry` (со стектрейсом),
`MetricLogEntry` (с числовым значением).

Реализуйте минимум двух посетителей:

* форматирование в текст;
* подсчёт статистики (сколько записей каждого типа).

**Требование:** добавление третьего посетителя не должно требовать правки
ни одного класса записи.

**Двойная диспетчеризация обязательна.** Решение через `is`, `switch` по типу
или сопоставление с образцом не засчитывается — это ровно тот тупик,
из-за которого паттерн и существует.

Метод `Accept` должен быть переопределён в **каждом** конкретном классе записи.
Вынести его в базовый класс нельзя — разберитесь почему, это контрольный вопрос.

### 3. Наблюдатель — подписчики на события конвейера

Минимум три подписчика:

* счётчик обработанных записей;
* алерт на записи уровня `Critical`;
* писатель в консоль.

Требования:

* **отписка реализована и показана в тесте**;
* исключение в одном подписчике не мешает остальным получить уведомление.

### 4. Push и pull

Реализуйте обе модели уведомления:

* **push** — источник передаёт данные в уведомлении;
* **pull** — источник сообщает о факте, подписчик сам забирает что нужно.

В отчёте объясните, какая где уместнее и почему.

### 5. Дополнительно, на 5 баллов

Замените прямые вызовы между конвейером и импортёром на
[Посредника](../Textbook/Поведенческие/Mediator.md): при перегрузке конвейер
должен приостанавливать импортёр, **не имея на него ссылки**.

Образец: `dotnet run --project Implementation -- mediator`.

## Типичная ошибка

**Посетитель через проверку типов.**

```csharp
// Так делать нельзя — это не Посетитель
public void Save(LogEntry entry)
{
    if (entry is ExceptionLogEntry ex) { ... }
    else if (entry is MetricLogEntry m) { ... }
}
```

Компилятор такой код собирает, и на первый взгляд он даже проще. Проблема
вылезает при добавлении четвёртого типа записи: программа продолжит
собираться, а новый тип молча уйдёт в ветку `else` и обработается неправильно.

При правильной двойной диспетчеризации добавление типа записи **ломает
компиляцию всех посетителей** — и компилятор перечислит все места,
которые нужно доработать. Это не недостаток, а главное свойство паттерна.

## Контрольные вопросы

1. Почему в Посетителе нужна двойная диспетчеризация? Что мешает обойтись
   обычной перегрузкой методов?
2. Почему `Accept` нельзя вынести в базовый класс иерархии?
3. Главный недостаток Посетителя — что произойдёт при добавлении нового типа записи?
4. Что случится с Наблюдателем, если подписчик бросит исключение? Как защититься?
5. Откуда в Наблюдателе берётся утечка памяти и как она лечится?
6. Чем цепочка обязанностей отличается от обычного списка обработчиков в цикле?
7. Что произойдёт, если запрос дойдёт до конца цепочки и никто его не обработает?
8. Чем Посредник отличается от Наблюдателя?
