# IoC и внедрение зависимостей

Материал занятия 3 и лабораторной работы 2.

Продолжение главы [SOLID](SOLID.md): принцип DIP говорит, что зависимости должны
приходить снаружи, — здесь разбирается, откуда именно они приходят и кто их создаёт.

---

## Три термина, которые путают

Их регулярно используют как синонимы, хотя это три разные вещи разного масштаба.

| Термин | Что это | Масштаб |
|---|---|---|
| **IoC** — Inversion of Control | Принцип: управление потоком передаётся наружу | Идея |
| **DI** — Dependency Injection | Приём: зависимости передаются извне, обычно через конструктор | Техника |
| **DI-контейнер** | Библиотека, которая собирает граф объектов автоматически | Инструмент |

Соотношение: DI — частный случай IoC; контейнер — необязательный инструмент для DI.

**Внедрение зависимостей возможно и полезно без контейнера.** Обратное неверно:
контейнер без понимания DI превращается в глобальную переменную с красивым именем.

### IoC шире, чем DI

Инверсия управления встречается и там, где никаких зависимостей не внедряют:

* [Шаблонный метод](Поведенческие/TemplateMethod.md) — базовый класс вызывает
  наследника, а не наоборот («не звоните нам, мы позвоним вам»);
* обработчики событий — фреймворк вызывает ваш код;
* `foreach` — [итератор](Поведенческие/Iterator.md) управляет обходом.

Общее у всех: **вызывает не ваш код, а вас**.

## Проблема

Класс, который создаёт свои зависимости сам, намертво связан с их типами:

```csharp
public class LogPipeline
{
    private readonly ILogSink _sink;

    public LogPipeline()
    {
        // Зависимость выбрана внутри. Подменить нельзя.
        _sink = new DatabaseLogSink("Server=prod;Database=logs;");
    }
}
```

Что отсюда следует:

1. **Тест невозможен.** Любая проверка `LogPipeline` идёт в боевую базу.
2. **Строка подключения зашита в код.** Сменить её можно только пересборкой.
3. **Класс знает о `DatabaseLogSink`,** хотя ему нужен только `ILogSink` —
   DIP нарушен, несмотря на наличие интерфейса.
4. **Время жизни зависимости неуправляемо.** Соединение открывается вместе
   с каждым конвейером, даже если конвейеров сто.

Наличие интерфейса само по себе ничего не даёт: важно, **кто выбирает реализацию**.

---

## Решение: зависимость приходит снаружи

```csharp
public class LogPipeline
{
    private readonly ILogSink _sink;

    public LogPipeline(ILogSink sink)
    {
        _sink = sink ?? throw new ArgumentNullException(nameof(sink));
    }
}
```

Изменение выглядит косметическим, но меняет всё: класс больше не решает,
с чем работать, и потому годится в любой сценарий, включая тестовый.

### Виды внедрения

| Вид | Как | Когда применять |
|---|---|---|
| **Через конструктор** | Параметр конструктора | По умолчанию: зависимость обязательна, объект нельзя создать недособранным |
| **Через свойство** | Публичный сеттер | Зависимость необязательна и имеет разумное значение по умолчанию |
| **Через метод** | Параметр метода | Зависимость нужна только одной операции |

**Внедрение через конструктор — выбор по умолчанию.** Оно даёт единственную гарантию,
которой нет у остальных: если объект создан, все его зависимости на месте.
Свойство можно забыть установить, и ошибка вылезет позже и в другом месте.

Признак, что с конструктором что-то не так: **в нём больше пяти параметров.**
Это не проблема DI, это сигнал нарушенного SRP — класс делает слишком много.
Правильная реакция — разделить класс, а не прятать зависимости в контейнер
или сервис-локатор.

## Композиционный корень

Если ни один класс не создаёт свои зависимости, кто-то всё же должен вызвать `new`.
Это делает **композиционный корень** — единственное место в приложении,
где собирается объектный граф.

```csharp
public static void Main(string[] args)
{
    // Композиционный корень. Единственное место с new для сервисов.
    var pipeline = new LogPipeline(
        new FileLogSource(args[0]),
        new PlainLogParser(),
        new SeverityFilter(LogSeverity.Info),
        new PlainFormatter(),
        new ConsoleSink());

    pipeline.Run();
}
```

Такой подход называют «DI для бедных» — название неудачное, потому что
для небольших приложений это лучший вариант: явно, отлаживается,
ошибки видит компилятор.

Требования к корню:

* **Он один.** Два корня означают два разных графа объектов и разное поведение
  в зависимости от точки входа.
* **Он на самом верху.** В `Main`, в `Startup`, в `Program` — там, где известно всё
  о конфигурации, но ещё ничего не началось.
* **Больше нигде `new` для сервисов нет.** Данные (`LogRecord`, `DateTime`, коллекции)
  создавать где угодно можно и нужно — правило касается только сервисов.

Рабочий пример: `dotnet run --project Implementation -- ioc`

## DI-контейнер

Когда сервисов становится десятки, ручная сборка превращается в простыню.
Контейнер делает ту же работу автоматически: он знает, какая реализация
соответствует какому интерфейсу, и разрешает граф по цепочке.

```csharp
var services = new ServiceCollection();

services.AddSingleton<ILogFormatter, PlainFormatter>();
services.AddSingleton<ILogSink, ConsoleSink>();
services.AddTransient<LogService>();

using var provider = services.BuildServiceProvider();

// Единственное обращение к контейнеру во всём приложении.
var service = provider.GetRequiredService<LogService>();
service.Log("Warning", "Место на диске заканчивается");
```

Контейнер сам увидит, что `LogService` требует `ILogFormatter` и `ILogSink`,
найдёт зарегистрированные реализации и создаст их.

### Смена поведения без перекомпиляции

```csharp
if (config.Format == "json")
{
    services.AddSingleton<ILogFormatter, JsonFormatter>();
}
else
{
    services.AddSingleton<ILogFormatter, PlainFormatter>();
}
```

`LogService` при этом не меняется. Именно это проверяется в лабораторной работе 2:
два профиля конфигурации должны менять поведение системы, не задевая код сервисов.

## Времена жизни

Контейнер решает не только «что создать», но и «когда создавать заново».

| Время жизни | Когда создаётся | Для чего |
|---|---|---|
| **Transient** | На каждое разрешение | Сервисы без состояния, дешёвые в создании |
| **Scoped** | Один на область видимости (запрос, операция) | Соединение с БД, единица работы, контекст пользователя |
| **Singleton** | Один на весь контейнер | Конфигурация, кэши, дорогие клиенты |

Демонстрация на счётчиках экземпляров:

```bash
dotnet run --project Implementation -- ioc-lifetimes
```

### Захваченная зависимость

Самая частая ошибка при работе с временами жизни: singleton, который зависит
от scoped-сервиса.

```csharp
services.AddScoped<IDbConnection, SqlConnection>();
services.AddSingleton<LogService>();   // а внутри — IDbConnection
```

Singleton создаётся один раз и навсегда сохраняет ссылку на то соединение,
которое существовало в момент его создания. Область давно закрылась,
соединение разорвано, а singleton продолжает им пользоваться.
Это называется **captive dependency**.

Ловится на старте, если строить провайдер с проверкой областей:

```csharp
services.BuildServiceProvider(validateScopes: true);
```

В ASP.NET Core эта проверка включена по умолчанию в среде разработки —
и её не стоит отключать.

## Singleton в контейнере против паттерна Singleton

Разница принципиальная, хотя слово одно.

| | Паттерн [Singleton](Порождающие/Singleton.md) | `AddSingleton` в контейнере |
|---|---|---|
| Кто гарантирует единственность | Сам класс, приватным конструктором | Контейнер |
| Как получают экземпляр | `ConfigService.Instance()` | Через конструктор |
| Класс знает, что он одиночка | Да | Нет, это обычный класс |
| Можно подменить в тесте | Нет | Да |
| Можно создать второй для теста | Нет | Да |
| Тесты зависят от порядка выполнения | Да | Нет |

Ключевое отличие: **`AddSingleton` управляет временем жизни, а паттерн Singleton
навязывает способ доступа.** Первое — решение об инфраструктуре, второе —
жёсткое ограничение, зашитое в класс навсегда.

Практический вывод: если нужен один экземпляр — регистрируйте обычный класс
как singleton в контейнере. Приватный конструктор и статический `Instance()`
не понадобятся почти никогда.

Разбор с кодом и тестами, показывающими разницу, — в главе
[Singleton](Порождающие/Singleton.md), раздел «Singleton против Dependency Injection».

## Service Locator — чего делать не надо

Соблазнительная альтернатива: раздать всем ссылку на контейнер.

```csharp
// АНТИПАТТЕРН
public class LogPipeline
{
    public void Run()
    {
        var sink = ServiceLocator.Current.GetService<ILogSink>();
        ...
    }
}
```

Почему это хуже внедрения через конструктор:

1. **Зависимости не видны в сигнатуре.** Чтобы узнать, что нужно классу,
   придётся прочитать все его методы.
2. **Ошибка обнаруживается в рантайме.** Забыли зарегистрировать сервис —
   узнаете от пользователя, а не от компилятора.
3. **Каждый класс зависит от контейнера.** Появилась глобальная зависимость,
   которой раньше не было.
4. **Тест требует настройки локатора.** Вместо `new LogPipeline(mock)` —
   регистрация в статическом контейнере и его сброс после теста.

Марк Симан назвал это антипаттерном, и с тех пор формулировка не оспаривалась.
Исключение одно: legacy-код, куда внедрение конструктором не заводится
без большого рефакторинга; тогда локатор используют как временную меру
на границе старого и нового кода.

## Плюсы и минусы

### Плюсы

* Классы тестируются изолированно: зависимость подменяется моком или стабом.
* Реализацию можно сменить конфигурацией, не трогая код.
* Граф объектов и все решения о времени жизни собраны в одном месте.
* Зависимости класса видны в сигнатуре конструктора — документация не нужна.
* Слои приложения перестают зависеть друг от друга напрямую (DIP).

### Минусы

* Порог входа: нужно понимать, где корень, кто что регистрирует и на сколько живёт.
* Ошибки конфигурации контейнера ловятся в рантайме, а не при компиляции.
* Стек вызовов и отладка усложняются: непонятно, откуда взялся объект.
* Легко скатиться к «регистрируем всё подряд» и получить сотню интерфейсов
  с единственной реализацией.
* Контейнер провоцирует прятать нарушения SRP: конструктор на десять параметров
  собирается автоматически, и проблема перестаёт быть заметной.

---

## Когда НЕ применять контейнер

* **Маленькое приложение.** До полутора-двух десятков сервисов ручной
  композиционный корень нагляднее и надёжнее.
* **Библиотека.** Библиотека не должна навязывать потребителю свой контейнер.
  Правильно — предоставить конструкторы с зависимостями и, если нужно,
  метод расширения `AddMyLibrary(this IServiceCollection)`.
* **Консольная утилита на один запуск.** Прямая сборка объектов короче и понятнее.
* **Когда контейнер используется как сервис-локатор.** Тогда он вредит,
  а не помогает: см. раздел выше.

Но внедрение зависимостей через конструктор применимо всегда —
оно не требует ни контейнера, ни библиотек.

## Вывод

Инверсия управления — это принцип, внедрение зависимостей — приём,
контейнер — инструмент. Порядок освоения именно такой, и пропускать шаги не стоит:
контейнер, взятый без понимания DI, обычно превращается в сервис-локатор
и делает код хуже, чем он был.

Практический минимум, которого достаточно для большинства задач:
**зависимости через конструктор, один композиционный корень, никаких `new`
для сервисов за его пределами.** Контейнер добавляется тогда, когда ручная
сборка перестаёт помещаться на экран, — и ничего в архитектуре при этом
менять не приходится.
